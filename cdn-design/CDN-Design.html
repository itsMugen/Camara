Images CDN on premise

Scope. The brief's cluster is one full site: identical nodes that all hold every image. Going beyond the brief, two full sites hold everything and stay in sync, cache-only locations in other regions are plain Nginx in front of them, and GeoDNS routes users to the nearest healthy location. The node software is the same either way. Figures 1–3 in §2, architecture diagram in §3.

The design in five decisions.

  1. An image's ID is the SHA-256 of its bytes. Images are never changed or deleted, so copies can never conflict, uploads are idempotent, every copy is self-verifying, and URLs are cached forever.
  2. Every node in a full site holds every image. A cluster is a set of identical nodes, each running Nginx and a small Go service over local disk. No master, no central database, no broker, no coordination service.
  3. Upload = push to every peer, 201 after the second copy. The receiving node pushes in parallel to its local peers and to one responsible node in the other site, which fans out locally. In sync, each image crosses the slow link once.
  4. Read = serve locally, else fetch from a peer, verify, keep, serve. Local peers first; the other site only if none has it or none answers within 50 ms. 404 only when every node confirmed absence, 503 when one didn't answer.
  5. Resync = per-peer change feed with a cursor. Each node numbers its images in arrival order. A restarted, rebuilt or brand-new node reads every peer's feed from its last cursor and pulls exactly what it is missing, newest first, while already serving traffic. One mechanism covers sync, recovery and new capacity.

2How it works

Three flows, one per requirement of the brief. A full site is one cluster of identical nodes that all hold every image. The second full site and the cache-only locations are the extensions described in §3; they add resilience and reach without changing the node software.

Upload · requirement 1

POST /images

  1. The uploader's nearest full site receives the upload. One node streams it to a temporary file, computing the SHA-256 as it goes and checking type and size.
  2. It saves the file under its hash and records it in its index.
  3. In parallel, it pushes the image to every other node in its site and to the responsible node in the other full site: the node picked by hashing the image ID over that site's node list, so every node agrees without coordination.
  4. As soon as one other copy is confirmed (normally a local peer, within milliseconds) it answers 201. The image is on 2 disks.
  5. The node in the other site passes it on to every other node in its site. A failed push is retried, and anything still missing is picked up by the change feed.
Read · requirement 2

GET /images/{id}

  1. GeoDNS sends the user to the nearest location: a full site or a cache.
  2. At a cache: a hit is served straight away. A miss is fetched from the nearest full site, stored, and served.
  3. At a full site: Nginx serves the file from memory or disk with a cache forever header. This is nearly all traffic.
  4. On a miss there, the node asks its local peers, then the other full site. It checks the hash, saves and serves. 404 only if every node said no; 503 if some didn't answer.
Resync · requirement 3

A node or a site comes back

  1. Every node numbers the images it stores in arrival order: 1, 2, 3… This is its change feed.
  2. Each node remembers, for every peer, the highest number up to which it has stored everything: its cursor into that peer's feed.
  3. A node catches up from all its local peers in parallel over the fast local network, newest images first (most views happen in an image's first days, §4), at full speed while it is quiet and slower as its own traffic rises. A whole site catches up from the other site, each missing image crossing once.
  4. Both serve traffic from the first second. Anything not copied yet is fetched on demand. Caches never need to resync.

One mechanism covers sync, recovery and new capacity. The change-feed loop also runs while everything is up, every few seconds against the local peers and every ~30 s against the other site, as a safety net for lost pushes. A new node or a rebuilt site is simply one whose cursors start at zero. The feed cannot skip anything: a node numbers an image only once the file is safely on disk, numbers are handed out one at a time, and a cursor only moves past images already stored. That's why there's no message broker and no separate recovery protocol.

Design decision: when is an upload "done"? By default, after 2 copies, preferring the local site. Confirmation takes milliseconds and doesn't depend on the link between sites. The cost: if a whole site is destroyed in the fraction of a second before its push to the other site completes, those few images are lost.

Uploaders that can't accept that can ask for one copy in the other full site before the 201, per uploader, identified by its API key. That costs one round trip between sites (10–50 ms) per upload. Making it a per-uploader choice keeps the common case fast without hiding the trade-off. If the two sites are close together (details §3), the cross-site round trip is cheap and confirming in both sites becomes the default.

3Architecture

Two full sites built the same way: identical nodes behind a load balancer, syncing over the fast local network, and syncing with the other site over the slower link, with each image crossing it once in sync. Cache locations sit in front of them and take no part in sync. The only coordination anywhere is nodes talking to each other over HTTP.

The decision everything else depends on: an image's ID is the SHA-256 hash of its bytes. Images are never changed or deleted, so the image set only ever grows. Copies can never conflict, uploading the same image twice does nothing, any copy can be checked against its own name, and URLs can be cached forever. That last property is what makes cache-only locations so simple: a cached image can never be out of date.

Each node runs two processes: Nginx and a small Go service with a local SQLite index. Each full site adds a load balancer pair, each cache location is just Nginx, and GeoDNS routes users. There is no master, no central database, no message broker and no coordination service.

Full sites and cache-only locations

Locations play two different roles. Full sites are the source of truth and hold every image; this is where the exercise's sync requirements are met. Cache-only locations are cheap outposts that keep popular images near users in other regions.

Why 2 full sites, not 1

Storage must survive losing a location

A cache always needs an origin behind it. With a single full site, losing it would lose images that exist nowhere else, stop all uploads, and make every cache miss fail. With 2, either one can go down and the system keeps working. Two is the minimum; a third is a capacity decision (§4).

Why not only caches

Caches are great for popular images, poor for rarely viewed ones

With the retrieval pattern assumed in §4, a cache serves about 90% of requests locally. If most images were viewed only once or twice, nearly every request would miss and travel to a full site anyway. Caches extend reach; they don't replace the origin.

4Assumptions and sizing

The exercise leaves scale and usage open, so the design is checked at three scales, profiles S, M and L, and sized for M. These are planning numbers to confirm with the business, not facts.

  • Infrastructure: two full sites far enough apart to serve different regions, 10 GbE inside a site (25 GbE at profile L), a private link or VPN with 10–50 ms round trip between sites, no cloud. Fewer locations shrink the topology, not the software (details §3).
  • Users: public downloads from browsers and apps, about 60% near the full sites and 40% in other regions. Uploads come from internal services only and never from the internet.
  • Images: JPEG, PNG, WebP, AVIF or GIF, about 500 KB on average, capped at 25 MB by the API (details §9), never changed and never deleted. The dataset only grows.
  • Traffic: photo-like. A few images get most of the views, mostly in their first days, so a cache in another region serves about 90% of its requests locally. Peaks are about 5× average, and everything is sized for peak.

Why 2 nodes per full site: a site survives a server failure or upgrade, and every upload is confirmed on 2 nodes. With two full sites, each must carry all origin traffic alone while the other is down, so each keeps 100% spare capacity. That is affordable because caches absorb most of the traffic from other regions: at M the worst case is about 640 requests/s at one site, a light load for two servers. Storage never sets the node count: even at L, every node still holds every image on one dense storage server.

What failsWhat users seeWhat the system does

Node dies during an uploadThe client gets an error and retries. Same bytes, same ID, so no duplicate.Nothing to do.
Disk lostNothing. The node serves what it has and fetches the rest on demand.A full copy from the local peers over the LAN, about 3 h at M and 20 h at L for the full dataset over the LAN, while serving traffic.
Silent disk corruptionAt worst one corrupt file, until the re-hash catches it.Every copy that moves between nodes is hash-checked, so corruption never spreads. A slow background re-hash finds bad local files and re-fetches them.
Bug, operator mistake, ransomwareBad data on both sites until it is restored from backup.Two sites survive losing hardware, not bad data written everywhere. An off-site, write-once backup reads the change feed like a node (details §8).

Consistency model: eventually consistent copies, but every read gives the right answer. After a 201, a GET for that ID returns the exact bytes at every node at once and at every cache within 10 s (a cache repeats a 404 it gave in the previous 10 s), as long as one node holding the image is reachable. Otherwise it returns 503, never a wrong 404. The one exception is a file corrupted on a node's own disk, which the background re-hash catches. No consensus protocol is needed: the image set only grows and IDs are content hashes, so two nodes can never disagree about what an ID means.

6Tools we chose not to use (yet)

Each of these is a reasonable choice a reviewer might expect in a CDN design. None is needed for the requirements at the target size, and each adds something to run, upgrade and debug at every location.

  • Message broker (NATS, Kafka): push plus the change feed already give fast delivery and exact catch-up. Add one when other systems want the event stream.
  • Central metadata database: a single point of failure and a cross-site hop for every miss. Names and ownership belong in the application that uses the CDN.
  • Distributed object store (Ceph, MinIO): built to spread data, not to copy everything everywhere. Far heavier than Nginx plus one small Go service per node.
  • Commercial CDN: our cache servers do the same job on hardware we control. Reconsider when users appear where we have no hardware.
  • BGP anycast: GeoDNS gives nearest-location routing without running BGP everywhere. Worth it when failover must take seconds.
  • Hash-based placement: while every node holds everything, nothing needs placing. Reconsider past ~0.5 PB, if the business agrees to drop "every node has every image".
  • Kubernetes: a few fixed, disk-heavy machines per location gain little from an orchestrator.
  • Image resizing and format conversion: not asked for. Usually the biggest egress saving once mobile bandwidth matters.
