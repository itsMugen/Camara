2How it works

Expands §2 of the design, whose figures 1–3 show the three flows. Each block below covers one part of them: the upload path, how the two full sites stay in sync, what a cache-only location runs, why the change feed cannot miss an image, and what happens on a read miss.

Upload validation, durability, edge cases

  • Never buffered in memory: the body streams to a temp file. SHA-256 is computed while streaming, the 25 MB limit is enforced, and the format is detected from the file's first bytes against an allow-list (JPEG, PNG, WebP, AVIF, GIF), never from the client's file name.
  • Crash-safe write: write temp file → fsync → insert a pending index row → rename into place → mark the row stored, which assigns its sequence number. A crash leaves nothing, a pending row without a file, or a complete file with a pending row; startup resolves both in one cheap query.
  • Same image twice (even at both sites at once): same hash, same file name. If the index has a stored row, the bytes are not written again, but the node still runs the push and 2-copy confirmation before answering 200, so a repeated upload never confirms an image held on one disk only. A file with only a pending row is completed the same way. Two concurrent uploads of the same bytes on one node are merged by ID: the second waits for the first.
  • Local peers down: the confirmed copy in the other full site counts as the second copy. Uploads keep working with one node per site.
  • Sites cut off from each other: uploads still succeed with 2 local copies. They reach the other site through the change feed when the link returns. An upload that asked for cross-site durability keeps its local copies and answers 503 with Retry-After; the uploader should retry the same site later rather than fail over, since the other site can do no better during a partition.
  • Propagation target: every node in the uploader's site has the image within ~100 ms of the 201 (500 KB takes under 1 ms on a 10 GbE link). The other site has it within one round trip plus transfer time, typically under 200 ms. Measured as "time from 201 to the last node holding the image" (p50/p99).
  • Failed push: retried 3× with backoff (100 ms, 500 ms, 2 s); a cross-site push then tries the next node in hash order (below), and anything still missing is left to the change feed. Worst case is one poll interval: a few seconds inside a site, ~30 s between sites. Meanwhile, figure 2 of the design covers any GET.
  • No second copy possible anywhere: 503 rather than confirm an image that exists on one disk only. The client retries, which is safe because uploads are idempotent.

Sync between the full sites each image crosses once

  • One node per site is responsible for each image. A hash of the image ID over the site's node list picks it, so every node agrees with no coordination and the work spreads evenly. The uploading node pushes to that node in the other site, and it alone fetches the image across sites during catch-up. It then passes the image to every other node in its site over the LAN.
  • Why it matters: without this rule, every node in a site would pull every image across the slow link, multiplying cross-site traffic by the number of nodes per site.
  • If the responsible node is down: the pusher, once its 3 retries fail, pushes to the next node in hash order instead. A node treats a local peer as down after two consecutive failed feed polls, and while it is down the next node in hash order also polls the other site for the IDs that hash to the absent node. Two nodes briefly disagreeing costs at most one duplicate transfer, never a miss, because the change feed catches everything regardless.
  • A cut-off site reconnects: its responsible nodes read the other site's feeds from their saved cursors and pull what's missing. Catch-up between sites is capped so it doesn't saturate the shared link (catch-up inside a site is throttled to the live traffic of both the fetching and the serving node instead). Images that users ask for are fetched first, on demand. The other site likewise pulls the uploads the first one accepted in the meantime. Images are immutable, so there's nothing to merge or resolve.
  • Polling cost: an empty change-feed response is a few hundred bytes. Polling the other site every 30 s is negligible traffic.
  • Adding a node changes the hash order, so it's done in two steps. Membership is static: one versioned node list, rolled out by Ansible, and every internal request carries the sender's list version so a mismatch is logged. Step 1: the new node is added to every peer's list as a feed source and push target only. It starts with all cursors at 0, pulls everything from its local peers (the "disk lost" case in design §5). It joins the load balancer as soon as it passes health checks and serves misses on demand like any node. Step 2: once its replication lag is zero, it is added to the responsible-node hash order. During the rollout of either step, two peers may briefly disagree about which node is responsible for an image. The result is at most one duplicate cross-site transfer per affected image, never a missed one, because the change feed catches everything regardless. Removing a node is the same two steps in reverse. Replacing a failed node is step 1 with the old name, then step 2.

Cache-only locations stock Nginx, a few settings that matter

proxy_cache_path /cache levels=2:2 keys_zone=img:1g max_size=3500g inactive=60d;   # 1 GB of keys ≈ 8M images: matches 3.5 TB at 500 KB
proxy_cache_lock on;                            # concurrent misses → one fetch
proxy_cache_valid 200 206 365d;                 # never revalidated: URLs are immutable
proxy_cache_valid 404 10s;                      # don't remember "missing" for long
proxy_next_upstream error timeout http_503;     # nearest full site first, then the other
  • Upstreams: both full sites, nearest first. If it is down, the cache falls back to the other one automatically.
  • Misses for the same image are merged (proxy_cache_lock), so a burst of requests for a new image costs one fetch per cache, not one per user.
  • Eviction: when the disk is full, the least recently used images go first. The cache never has to know which images exist.
  • Restarts: the cache lives on disk, so a restart keeps it. Only a brand-new or replaced cache server starts empty and warms up from traffic.
  • Read-only: uploads and internal endpoints are not served (405). Uploaders always talk to the full sites.
  • Trust: it fetches from the full sites over TLS, so it serves exactly the bytes they verified. Optionally it can re-check the hash, since the ID is in the URL.

Change feed why it is correct

GET /internal/changes?since=41870&limit=1000
→ { "epoch": "b2-7f3a", "items": [ {"seq":41871,"id":"ab12…","ext":"jpg","size":482113}, … ], "next": 42870 }
  • Startup sequence:
    1. Delete leftover temp files. Resolve every pending index row: file present, mark it stored and assign its sequence number; file absent, delete the row. One indexed query, not a scan of millions of files.
    2. Start serving reads straight away: fetch-on-miss covers the gap.
    3. Read the feed of every reachable peer in the node's own site from its saved cursor. The other site is read only if no local peer is up, or, on the next node in hash order, for the IDs of a local peer that is down. Merge the feeds and skip duplicates by ID. This is the catch-up phase; once the local backlog is done, the steady-state loop takes over: every few seconds against local peers and, on the nodes responsible for cross-site sync, every ~30 s against the other site.
    4. Fetch the missing images newest first (most views happen in the first days after upload, §4), spread across all peers that hold them, with parallel workers.
    5. Throttle adaptively: full speed while the node's own traffic is low, backing off as it rises ("Fast but polite" below).
    6. For each peer, move the cursor only up to the highest sequence number with every image below it stored and fsynced. Workers finish out of order, and this way a crash during catch-up never skips an image. With newest-first fetching, the cursor jumps forward only when the backlog is finished. A crash before then costs one re-read of the backlog's metadata: a few MB after an outage of hours, a couple of GB at M and tens of GB at L (minutes of paging, no file re-downloaded) during a full rebuild. Images already on disk are skipped by ID and never downloaded again.
  • No gaps: a sequence number is assigned only when the row is marked stored, after the file is in place, inside the same write transaction, and SQLite commits one write at a time. Numbers therefore appear in order, so a cursor can never skip an image that shows up later with a lower number.
  • Any one peer is enough: each feed lists everything that peer holds, wherever the image came from. A returning node misses nothing as long as one peer it reads from was up. Duplicates are skipped by ID.
  • Index rebuilt on a peer: the feed carries an epoch that changes whenever the index is rebuilt. A reader that sees a new epoch resets its cursor for that peer to 0. That costs one metadata scan; files already present are not transferred again.
  • Fast but polite: catch-up runs at full speed while the node's own traffic is low and backs off as live traffic rises, rather than using a fixed cap. Catch-up between sites keeps a fixed cap, because that link is shared. Popular images arrive first anyway, because users ask for them. The back-off applies at both ends: the source peer also limits what it serves to catch-up based on its own live egress, because during a rebuild the empty node's traffic is mostly misses it proxies to that peer, and with 2 nodes per site the serving peer is the node that must stay fast.
  • How quick: a one-hour outage at M is about 1,000 images (≈0.5 GB): seconds over the LAN, under a minute across sites. A replaced, empty disk copies everything from its local peers in parallel, limited by its network card: about 3 h at M (~14 TB at 10 GbE) and about 20 h at L (~220 TB at 25 GbE), at full speed; longer if it runs through peak hours. The node serves traffic throughout, with misses fetched on demand, and the site still has its other node(s). A slow rebuild costs bandwidth, not availability. This is the price of every node holding every image (§4).

Read on a miss at a full site nearest first, 404 vs 503, integrity

  • Nearest first, but don't wait too long: ask the local peers. If they don't have the image, or haven't answered within ~50 ms, ask the other site's nodes in parallel; the first to start streaming is kept and the other request is cancelled, so a miss crosses the link once. The copy is verified before it is served.
  • One budget: the whole miss has a budget of ~2 s. A node that has not answered within it counts as "didn't answer" for the rule below, so a slow local peer can delay a miss but never turn it into a wrong 404.
  • Integrity: the downloaded file is re-hashed before it's saved or served. A corrupt copy is discarded and fetched elsewhere. A 200 always carries the right bytes.
  • Verify, then serve: the node downloads and checks the whole image before sending the first byte. That costs ~20 ms on the LAN, and a few hundred ms from the other site for the largest images, once per node. Streaming before verifying would be faster but could send corrupt bytes, so it was rejected.
  • Concurrent misses for the same image are merged into one download (Go singleflight).
  • Honest errors: 404 only when every node answered "don't have it". If any node didn't answer (for example the other site is cut off), 503, because the image might be there. Errors are never cached for long: a cache keeps a 404 for 10 s, and a node's short memory of a miss is cleared the moment the image arrives by push or fetch.
  • Junk IDs are rejected before touching disk or network (64 lowercase hex characters). Repeated misses for the same ID are remembered for a few seconds, so probing doesn't cause traffic between sites.

3Architecture

Expands §3 of the design: how users reach the nearest location, how the topology changes with the locations the company actually has, and what runs on each machine.

Routing: GeoDNS sends users to the nearest healthy location failover, alternatives, site vs cache

cdn.example.com resolves to the nearest location, full site or cache, through self-hosted authoritative DNS servers (PowerDNS with GeoIP, one at each full site). The DNS servers health-check each one and stop handing out a location that is down. With a 20 ms round trip and a new TLS connection, the network costs about 60 ms and a hit under 10 ms. From another continent the same request takes ~450 ms, which is exactly what a nearby cache removes.

  • Failover time: DNS answers carry a short TTL (60 s). When a location fails its health checks, new lookups go elsewhere within about 1–2 minutes. If a cache goes down, its region is sent to the nearest full site: slower, but everything still works. Node failures inside a full site are handled by its load balancer in seconds, so DNS only reacts to whole locations.
  • Why not BGP anycast: anycast fails over in seconds, but it requires running BGP with the upstream providers at every location. Worth it if the network team already does. GeoDNS is the simpler start.
  • Site or cache for a new region? A cache if its users mostly view images that others view too, and a cache miss of 100–200 ms is acceptable. A full site if its traffic is large and spread over many rarely viewed images, if it uploads heavily, or if the business wants a third permanent copy.
  • Uploaders never use GeoDNS. Each full site has a fixed internal hostname (upload-a.cdn.internal, upload-b…) that resolves to that site's virtual IP on the internal DNS. An uploading service is configured with its nearest site first and the other as fallback, and switches on connection errors; a 503 means retry the same site after Retry-After, not fail over. The upload endpoint is not reachable from the public hostname at all.
  • Questions for the business: where are the users today and in two years, what load time is acceptable, how often is a typical image viewed, and may images sit on third-party infrastructure (a commercial CDN can replace our own caches)?

Fitting the on-premise infrastructure that exists one data centre · two close sites · two distant sites

"On premise" means we work with the locations the company already has, and that may be fewer than this design assumes. The baseline needs two sites far enough apart to serve different regions. If they don't exist, the topology shrinks, but the software stays the same: a peer in another rack, another building or another country is the same HTTP call. Three things change: which failures the system survives, when an upload counts as done, and whether caches are possible.

How the numbers were derived back of the envelope

  • Requests: from Expected image retrieval, above: 60 image requests per active user per day, average = requests/day ÷ 86,400, peak ≈ 5× average.
  • Origin traffic: 60% of requests come from users near the full sites; the other 40% go to caches, which serve ~90% of them (photo-like traffic, images viewed many times). At M: 600 + 400 × 10% ≈ 640 GETs/s reach the full sites at peak. With a long-tail workload the cache hit rate would be lower and origin traffic higher. That's the assumption to validate first (Expected image retrieval, above).
  • Egress: GETs × 500 KB, a deliberately conservative average. Serving resized and AVIF/WebP versions would typically cut it by 30–60%.
  • What sets the node count: read traffic with one node down, not uploads or storage. Replication is tiny next to reads (≈2 MB/s at M: one push to the local peer and one to the other site), and storage never sets it: even at L, ~220 TB after 4 years fits on one dense storage server, so every node keeps every image.
  • Cache size: the images a region views within a few weeks, not the whole dataset.
  • Storage growth: uploads/day × 500 KB × 365: about 3.6 TB a year at M and 55 TB at L.
  • Traffic between full sites is small: each image crosses once. At M: ~2 uploads/s at peak × 500 KB ≈ 1 MB/s. The link between sites only matters for catch-up and for rebuilding a whole site.

5Failures, guarantees and traffic patterns

Expands §5 of the design, which holds the failure table and the consistency model. As a client sees it, that model rests on three guarantees:

201

The image is safely on disk on at least 2 nodes: normally in the same site, or in both full sites if the uploader asked for it.

Any location

After a 201, every node can serve the image at once and every cache within 10 s, as long as one of its holders is reachable.

200 / 404

The bytes always match the ID, except a file corrupted on a node's own disk until the re-hash catches it. A 404 is always confirmed by every node, never a guess; a cache may repeat a confirmed 404 for up to 10 s, and a node for a few seconds unless the image reaches it first.

The retrieval pattern assumed in §4 is skewed, recency-heavy and peaky. This is how the design behaves under it, and under the cases that stress it most.

7Why content-addressed IDs the core decision

id   = hex(SHA-256(bytes))                     # 64 lowercase hex characters
URL  = https://cdn.example.com/images/{id}.{ext}
file = /data/{id[0:2]}/{id[2:4]}/{id}.{ext}    # 65,536 directories, none gets huge
  • Idempotent uploads, free deduplication: the same bytes always get the same ID, whichever site they're uploaded to.
  • No conflicts: two different images can't share an ID, so replicas are byte-identical by definition and syncing is just "copy what you're missing", even after the sites have been cut off from each other.
  • Built-in integrity: every copy can be checked against its own name, in transit and on disk.
  • Cache forever: Cache-Control: public, max-age=31536000, immutable and ETag: "{id}". Browsers, our cache locations and any proxy in between never revalidate.
  • Safe paths: IDs are validated against ^[0-9a-f]{64}$ before touching the file system.
  • Trade-off accepted: clients can't choose file names. A name-to-ID mapping belongs in the application that owns the names.
  • Trade-off accepted: the URL is an existence oracle. Anyone who holds an image's bytes can compute its URL and learn whether the CDN has it, and a second uploader of the same bytes learns the image already existed (200 instead of 201). For public product or editorial images that's harmless. If private images are ever stored, two fixes exist without changing the design: serve them behind signed URLs (§8), or make the public name HMAC(secret, id) while nodes keep using the SHA-256 internally. The second keeps every sync and integrity property between nodes and only costs browsers the ability to verify a file against its name.

8Operations essentials health, monitoring, security, backup

Health checks

  • Node read readiness depends only on the node itself: disk readable, not in maintenance. It deliberately does not depend on peers. Otherwise a network blip would make every node "unhealthy" at once, even though every node can serve its own copies.
  • Node write readiness also requires disk below 90% and at least one reachable peer (local or remote).
  • Location health for GeoDNS = the location serves a known test image. Each DNS server fetches that test image through the location's public address, never over the private link, so a full site cut off from the other but serving its users stays in rotation. A location is withdrawn only when its public service fails.
  • "Fully caught up" is not required anywhere: fetch-on-miss makes a lagging node correct.

What to monitor (Prometheus + Grafana per location, federated)

  • Replication lag, the key signal, inside each site and between the sites: images in peers' feeds that this node doesn't have yet, and the age of the oldest one.
  • Cache hit rate per cache location. It decides whether a region is well served by a cache or needs a full site.
  • Miss rate at the full sites, 404 vs 503 rates, p99 latency per path, traffic between sites, disk fill and days until full (alert at 90 days: on-premise hardware takes weeks to arrive).

Security

  • Uploads need a per-service API key and are accepted only at the full sites, from internal networks. GETs are public (or signed URLs if needed).
  • Node-to-node and cache-to-origin traffic uses TLS (mTLS between nodes) over private links or a VPN, and internal endpoints are never exposed through a balancer or a cache.
  • Uploads are checked for size, format and image dimensions. X-Content-Type-Options: nosniff and a strict CSP stop an image URL from serving active content.

Backup and takedown

  • Two sites are not a backup. They survive losing hardware, but a bug or a compromised admin account reaches both. A backup host reads the change feed like a node and writes to write-once storage, isolated from the CDN's credentials. Restores are tested twice a year.
  • Legal takedowns (court order, illegal content) happen even without a delete feature. A small blocklist, synced like the images, moves the file out of the served folder at both sites and answers 451, and a purge request removes it from every cache location. Re-uploads of the same bytes are blocked automatically. Copies already in users' browsers can't be recalled by any CDN. The blocklist is a file rolled out with the versioned node list (Ansible), applied before a node replays feeds, and a blocked ID counts as stored for the cursor rule above: the fetcher skips it without calling the peer, so catch-up never stalls on a removed image. The cache purge is a small script that deletes the cached file for that key on each cache server, since stock Nginx has no purge endpoint.

The ID alone identifies the bytes; the extension is recorded at upload from the detected format. A request with the wrong extension gets a 301 to the canonical URL, so there is exactly one cacheable URL per image. A bare /images/{id} works the same way.
PUT /internal/images/{id}Peer push (local, or to the other site's responsible node, which passes it on). The receiver verifies the hash before confirming.
GET /internal/images/{id}Peer fetch on a miss or during catch-up.
GET /internal/changes?since=NChange feed, paginated, with epoch.

10How the design would be tested proving the guarantees

  • Unit: ID validation, crash-safe write, change-feed paging and epoch reset, choice of the responsible node per site, the cursor staying below any missing image when workers finish out of order, and startup repair resolving pending rows (file present: stored with a new sequence number; file absent: row deleted).
  • Integration (Docker Compose: 2 "sites" × 2 nodes plus 1 cache, with added latency between sites): upload at site A, immediately GET at site B and through the cache; stop a node, upload 1,000 images, restart it and check it converges; p99 time from 201 to the last node holding the image stays under the target (~100 ms inside a site).
  • Fault injection (Toxiproxy, killing processes): cut the sites apart, upload on both sides, heal and check convergence; stop a full site and check the cache fails over; crash mid-upload and mid-catch-up; corrupt a file on disk; drop a push and check it is retried, then caught by the feed; kill a node halfway through a newest-first catch-up, restart it, and check it converges without downloading any file twice; add a third node to a site under load with the two-step rollout and check it serves correct bytes from the first second and no image is missed while the hash order changes.
  • Invariant check: record every 201, and after the chaos run assert that every confirmed image is readable and byte-identical from every node and through every cache.
  • WAN efficiency: count bytes between sites during a bulk upload, and assert each image crossed once.
  • Load (k6): hit, miss and upload paths at the profile-M peak, including one full site carrying everything.
